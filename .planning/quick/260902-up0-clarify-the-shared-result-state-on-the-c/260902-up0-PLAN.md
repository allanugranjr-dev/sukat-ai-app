# Quick Task: Clarify the shared result state on the customer results screen

## Goal

Make the customer results action clearly communicate that a provider result is already visible to the dressmaker's organization, including where the dressmaker reviews it. Preserve the existing organization-scoped sharing behavior and do not add a second delivery or notification path.

## Task 1: Make the shared state explicit in the results UI

- **Files:** `src/App.tsx`, `src/styles.css`
- **Action:** Use the existing `ready_for_review`/`verified` state to render a success-oriented sharing message instead of the contradictory “Check before sharing” copy. Keep the completed button disabled and label it as shared, add concise customer-facing guidance that the dressmaker can open the Reviews queue, and retain the existing send action for any result that is not yet shared.
- **Verify:** `npm run typecheck`; `npm test`; `npm run build`; inspect the mobile results layout for readable stacked action content and the desktop layout for aligned action controls.
- **Done when:** A shared result visibly says it is shared with the dressmaker and directs the recipient to the dressmaker Reviews queue, while the existing API/status behavior and responsive layout remain intact.

## Must-haves

- The customer can distinguish “ready to share” from “already shared.”
- The dressmaker destination is named as the Reviews queue.
- No existing auth, organization scope, scan status, or backend route is changed.
