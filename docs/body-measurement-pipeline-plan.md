# SukatAI body-measurement pipeline

This document records the implemented migration for the existing SukatAI
application. It preserves the current React/Vite screens, authentication,
Supabase tables/RLS/private Storage, Node/MariaDB runtime, XAMPP compatibility
path, role workrooms, and Three.js viewer.

## Active architecture

```text
front photo + side photo + actual height
  -> private asset authorization
  -> bounded image validation
  -> MediaPipe Lite pose validation
  -> OpenCV/foreground silhouette profiles
  -> real-world height calibration
  -> bounded CPU Anny parameter search
  -> CLAD-Body measurements from fitted Anny mesh
  -> Trimesh GLB export and reopen validation
  -> private Node/Supabase body-model storage
  -> existing interactive SukatAI viewer
```

Supabase or the Node gateway remains the authenticated orchestration boundary.
The Python service does not receive browser credentials and does not own user
records. The service accepts the required `front_image`, `side_image`, and
`height_cm` fields, returns a queued response quickly, and exposes a status
resource for the gateway to poll. The gateway writes authoritative progress and
only marks a scan complete after measurements, model storage, and the database
update succeed.

## Processing contract

The service exposes:

- `GET /health` — safe readiness diagnostics; paths and secrets are omitted.
- `GET /api/v1/body-scan/status` — backend, CPU, dependency, and asset state.
- `POST /api/v1/body-scan` — multipart front/side/height submission; optional
  back input is retained as diagnostic context.
- `GET /api/v1/body-scan/{scan_id}/status` — queued, validating, processing,
  completed, or failed progress. Completed responses include the authoritative
  measurements and model metadata.
- `GET /api/v1/body-scan/{scan_id}/model-file` — authenticated GLB delivery.

The durable database lifecycle is:

`queued` → `validating` → `processing` → `completed` or `failed`

The existing business review status remains separate:

`draft` → `uploaded` → `processing_queued` → `processing` →
`ready_to_share` → `ready_for_review` → `verified`

Provider progress is copied into `scans.processing_status` and
`scans.processing_progress`; it is never generated by a frontend timer. A
failure keeps progress below 100 and stores an actionable error.

## Low-end profile

The configured starting profile is deliberately CPU-first for the Lenovo
ThinkPad L380 target:

- CPU device forced; CUDA is not required.
- One active scan (`MAX_CONCURRENT_SCANS=1`).
- MediaPipe Lite task asset, about 6 MB, downloaded separately and ignored by
  Git.
- Maximum working image long edge of 1280 pixels.
- Anny coordinate search capped at 60 evaluations with early stopping.
- Three.js low-power rendering on mobile/low-memory/integrated-graphics
  devices, with reduced shadows and capped pixel ratio.

The installed CLAD-Body release requires Python 3.12 or newer, so the local
environment uses Python 3.14 and the Docker image uses Python 3.12. The
application does not install CUDA, NVIDIA wheels, SMPL/SMPL-X weights, or
large reconstruction checkpoints.

## Data and privacy

Front and side images remain in the existing private `scan-captures` bucket.
The gateway creates short-lived signed URLs for provider processing. The
generated GLB is stored in the existing private `body-models` bucket or the
Node private storage directory. Ownership and organization checks remain in
the existing Auth/RLS/server boundaries; the new lifecycle fields are backend
managed by migration triggers.

Automatic measurements retain their provider value, method, source, and
optional confidence. Tailor corrections remain separate in `adjusted_value`,
with reviewer and reason fields preserved. No confidence or accuracy value is
invented when the provider does not report one.

## Migration classification

### KEEP

- Existing customer, dressmaker, administrator, authentication, navigation,
  upload/camera, review, orders, fittings, notification, and profile flows.
- Supabase schema, private buckets, RLS, Auth triggers, and role boundaries.
- Node/MariaDB/Socket.IO runtime and the existing Three.js viewer.

### MODIFY

- Scan lifecycle and provider bridge to use durable status/progress fields.
- Python service boundary, calibration, Anny fitting, CLAD provenance, and GLB
  validation.
- Frontend polling, truthful failure states, provider model loading, and
  measurement-guide interactions.
- XAMPP compatibility behavior so it cannot silently present a local sample as
  a personalized scan.

### REPLACE

- The active deterministic/sample completion path with the CPU Anny + CLAD
  provider path.
- Synchronous/coarse processing transitions with queued asynchronous gateway
  processing and provider-status polling.

### LEGACY COMPONENT — SAFE REMOVAL NOT YET VERIFIED

- XAMPP's explicitly opt-in `SUKATAI_ALLOW_DEMO=true` reference result remains
  for UI-only demonstrations and is visibly labeled.
- Guarded PIXIE, SMPL-X, SMPL-Anthropometry, and old silhouette adapters remain
  isolated because their removal has not been proven unrelated to other project
  paths. They are not selected by the active Anny + CLAD pipeline.

## Verification and remaining decisions

Automated tests cover image/height guardrails, API queue/status behavior,
calibration, pipeline GLB reopening, provider response validation, scan-flow
navigation, and measurement mapping. A local system check confirms the CPU
MediaPipe Lite, Anny, CLAD-Body, OpenCV, SciPy, and Trimesh dependencies.

There is no consented tape-measurement reference dataset in the repository, so
no accuracy percentage is claimed. Before production tailoring, compare
predicted values with real reference measurements and record absolute and
percentage errors per subject. A hosted Supabase deployment also needs a
public HTTPS deployment of the Python provider and the corresponding Edge
Function secrets; a laptop `127.0.0.1` URL cannot serve Vercel/Supabase.
